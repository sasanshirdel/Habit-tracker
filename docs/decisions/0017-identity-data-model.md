# ADR-0017: Identity data model — users, credentials, sessions, single-use tokens

- **Status:** Accepted (P2-01)
- **Date:** 2026-11-25

## Context

PRD §3.11 (accounts and personalisation), §6 (identity entities, data integrity) and ADR-0005
(customer sessions, Argon2id, separate admin identity) need a schema before registration (P2-02),
guards (P2-03), verification (P2-04), recovery (P2-05), Google sign-in (P2-06), profile/preferences
(P2-07), session management (P2-08) and account deletion (P2-10) can be built. Backlog P2-01 (#21)
asks for UUIDv7 ids, a case-insensitive unique email, soft-delete fields, hashed session and token
storage, indexes and constraints.

## Decision

### Tables (migration `20261125060000_identity`, owned by the `identity` module)

| Table                       | Key             | Holds                                                                        |
| --------------------------- | --------------- | ---------------------------------------------------------------------------- |
| `users`                     | `id` UUIDv7     | `email` (citext, unique), `email_verified_at`, `deleted_at` (soft delete)    |
| `user_profiles`             | `user_id` (1:1) | `display_name` (1..100 chars, optional); avatar arrives with P2-07           |
| `user_preferences`          | `user_id` (1:1) | `locale` enum (`en`/`fa`, no default), `timezone` (IANA, 1..64), `theme`     |
| `user_password_credentials` | `user_id` (1:1) | `password_hash` — Argon2id PHC string only                                   |
| `user_sessions`             | `id` UUIDv7     | `token_hash` (32-byte SHA-256, unique), `expires_at`, `last_used_at`, revoke |
| `user_tokens`               | `id` UUIDv7     | `purpose` (`email_verification`/`password_reset`), `token_hash`, `email`     |

- **Ids:** UUIDv7 generated by the Prisma client in the application (`@default(uuid(7))`), stored
  as `uuid`. Child rows reference `users.id` with `ON DELETE CASCADE`, so the hard-delete step of
  account deletion (P2-10) removes everything that belongs to a user in one statement.
- **Names:** snake_case tables and columns (`@@map`/`@map`), PascalCase Prisma models.
- **Time:** every instant is `timestamptz(3)` (UTC). `updated_at` is maintained by Prisma.
- **Email:** `citext` (extension created by the migration; it is a _trusted_ extension, so the
  database owner needs no superuser rights). Unique **including soft-deleted accounts**, so an
  address cannot be re-registered while a deleted account is still restorable (see open decisions).
  The database also refuses values with surrounding whitespace, without an `@` after the first
  character, or longer than 254 characters; full normalisation and syntax validation is zod at the
  API edge (P2-02).
- **Passwords** live in their own table so an account may have no password (Google sign-in). A
  CHECK accepts only `$argon2id$v=19$…` PHC strings (≤ 512 chars), so plaintext or another
  algorithm can never be stored by mistake. Hashing and its dependency are chosen in P2-02.
- **Sessions and emailed tokens:** the client receives a 256-bit random token (32 bytes from the OS
  CSPRNG, 43 base64url characters); the database stores only `SHA-256(token)` (`bytea`, exactly 32
  bytes by CHECK, unique). A fast hash is sufficient because the input has 256 bits of entropy
  (nothing to brute-force, no salt needed); passwords, which are low-entropy, use Argon2id instead.
  No pepper/HMAC key for now (it would add a secret to manage; revisit if a threat model needs it).
  Primitives in `apps/api/src/modules/identity/secret-token.ts`: `issueSecretToken`,
  `hashSecretToken` (returns `null` for anything that is not a canonical token, so malformed and
  unknown tokens are indistinguishable), `secretTokenHashesEqual` (constant time).
- **Session lifetime:** `expires_at` is the absolute expiry (CHECK: after `created_at`); idle
  timeout is computed from `last_used_at` by the application. Revocation is
  `revoked_at` + `revoked_reason` (`sign_out`, `sign_out_everywhere`, `rotated`,
  `password_changed`, `account_deleted`), set together (CHECK). No IP address or user agent is
  stored yet (personal data; P2-08 decides what the session list shows).
- **Single-use tokens:** one table for verification and reset (`purpose` enum); `consumed_at` marks
  use; an email-verification token must carry the address it verifies (CHECK), so changing the
  email invalidates older links. Invalidating earlier tokens of the same purpose is application
  logic (P2-04/P2-05).
- **Indexes:** unique `users.email`, unique token hashes, `user_sessions(user_id)`,
  `user_tokens(user_id, purpose)`, and `expires_at` on both for clean-up jobs.
- **Constraints Prisma cannot express** (CHECKs, the extension) are written by hand in the
  migration SQL; `prisma migrate diff` reports no drift with them (tested), and a unit test keeps
  the application limits (`IDENTITY_LIMITS`, `PASSWORD_HASH_PREFIX`, `SECRET_TOKEN_HASH_BYTES`) in
  step with the SQL.
- **Module:** the Identity area starts as **one** feature module, `src/modules/identity`, owning
  all six tables. ARCHITECTURE §3 lists auth/users/profiles/preferences/sessions as the area's
  concerns; they are split into separate modules only if the code grows enough to need it.
- **Admin identities are not here.** Staff use `AdminIdentity` and admin sessions (Phase 10,
  ADR-0005); nothing in these tables can grant administrative power.

### Protection while no route uses the tables

P2-01 adds no HTTP route, job or UI. No code reads or writes these tables outside tests, so there
is nothing to authorise yet; the deny-by-default guard (P2-03) must exist before any route exposes
identity data, and rate-limit class `auth` (ADR-0011) applies to the auth routes of P2-02.

### Migration safety

Additive only (new extension, types, tables); a unit test fails if the migration contains a
statement-leading `DROP`/`TRUNCATE`/`DELETE`/`UPDATE` or a column/constraint drop. It is tested from
an empty database (integration global setup) and **from the previous release state** (all older
migrations applied first, then `migrate deploy`). Rollback before real data exists: drop the six
tables and four enum types.

## Alternatives considered

- **Lower-cased `email_normalized` text column instead of citext** — works without an extension
  but needs every query to remember the normalised column; citext makes the right comparison the
  default. Rejected.
- **Database-generated ids (`gen_random_uuid()` / PostgreSQL 18 `uuidv7()`)** — ADR-0006 says ids
  are generated in the application; Prisma's `uuid(7)` does that with no extra dependency.
- **Password hash on `users`** — simpler, but Google-only accounts would carry a null credential
  and the credential's own timestamps would mix with the account's. Rejected.
- **Separate tables per token purpose** — identical shape; one table with a purpose enum keeps
  clean-up and tests in one place.
- **HMAC-SHA-256 with a server key for token hashes** — protects against an attacker who can write
  to the database and read it, at the cost of a secret to rotate. Not needed for 256-bit random
  tokens today.

## Open decisions (interim choices, reversible; for the owner)

1. **Email stays reserved while an account is soft-deleted.** Safest interim: a deleted account
   cannot be taken over by re-registration during the restore window. The window length and what
   happens after it belong to P2-10. _Resolved by ADR-0025 (P2-10):_ 30-day grace period with an
   emailed restore link; afterwards the purge erases the account and the address is free again.
2. **No default locale** — the API must store the language the user registered in; the theme
   defaults to `dark` (ADR-0013).
3. **No IP/user-agent on sessions** until P2-08 decides what the session list shows and how long
   such personal data is retained. _Resolved by ADR-0023 (P2-08):_ only coarse browser/OS/device
   families are stored, never the raw user agent or an IP address; ended sessions are deleted 30
   days after they end.

## Consequences

- P2-02+ build on fixed, constraint-checked tables; mistakes such as storing a raw token or a
  plaintext password fail in the database, not only in review.
- Hand-written CHECKs must be kept in sync with the application constants (unit-tested) and must be
  repeated by hand in any later migration that recreates these tables.
- The architecture check's table-ownership follow-up (ADR-0016) now has real models to work with.
